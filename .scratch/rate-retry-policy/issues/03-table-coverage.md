# 03 · 表外端点怎么处置、表要不要全量补全

Type: grilling
Status: resolved
Blocked by: 02

## Question

`RATE_LIMITS` 现在只有 8 条，`okx/consts/endpoints/` 去重后约 274 个 `/api/v5/...` 路径在表外且不限流（`okx/consts/rate_limits.py` 与 README.md:113 都把这条写成了免责声明）。在 [采用哪个账户层级口径与文档快照](02-limit-scope.md) 的口径之下拍板：

1. 表外端点：继续「不限流」并保留 README 免责声明，还是按 02 定的兜底值统一限流？
2. 「全量补全」是**图内要做的决策**，还是明确留作图外施工？若留作施工，spec 里要写到什么程度——给判定规则即可，还是要给出最终表？
3. **覆盖目标决策归本工单**（2026-11-06 由 [采用哪个账户层级口径与文档快照](02-limit-scope.md) 迁入）：01 已确认官方没有全量端点表、数值分散在各端点详情页（约 135 个 REST 路径带 `Rate Limit:`），而项目有约 274 个 `/api/v5/...` 路径。「覆盖」的验收线按「官方已公布限额的端点」还是「全部端点」？02 只定数值口径，不在此重复拍板。
4. 表的维护成本：新增端点时谁负责补表？要不要一个测试断言「每个端点路径都在表里或显式豁免」？

注意：本图只决策，不动 `okx/consts/rate_limits.py`；补全 274 条是图外施工。

> **决策归属与前提修正（2026-11-06）**：
> - 第 1 点失效：02 的 Answer 第 2 条定的是「未收录端点维持不限流、**不设**统一兜底」，并未定任何兜底值。03 不重开这个决策；README.md:113 免责声明的具体行文归 [文档、CHANGELOG 与 ADR 怎么落](07-docs-and-adr.md)。
> - 第 2 点前半已被地图 Out of scope 定掉（补全属施工），仍开放的只有后半「spec 写到什么程度」。
> - 术语按 02 改：「表外端点」定名「未收录端点」（项目表未收录，非官方未公布）。

## Answer

覆盖策略已定（2026-11-06，HITL grilling，`/grilling` + `/domain-modeling`）。

**事实基线**（01 findings 第 38、87、89 行）：官方 `Rate Limit:` 标注 137 处、`HTTP Request` 块 141 个、distinct REST 路径 135 个，「几乎覆盖全部 REST 端点」，未发现成批「未列限额」的端点；官方明确区分「项目表未收录的路径」与「OKX 文档未列限额的端点」不是同一对象。但 findings 未穷尽逐一核验、只作统计性陈述。项目 `okx/consts/endpoints/` 去重 274 个路径，`RATE_LIMITS` 8 条；`test/unit/okx/test_retry.py:162-171` 只测 `RateLimiter`、无表覆盖断言。

1. **覆盖目标（验收线）**：按 **「官方已公布限额、且与项目路径常量对应的端点」**，不以 274 个路径常量为分母。理由：02 已定数值必须取官方端点详情页固定值，硬按 274 会逼出约 139 个没有官方对应值的路径去编数值或兜底（02 已否掉兜底）；findings 说官方几乎覆盖全部 REST 端点，两者实际差别主要在项目侧的路径冗余（别名 / 废弃端点 / 统计口径差异）。场景：`/api/v5/account/bills` 官方给 5/s、项目表未收录，两种口径下都该进表；只在项目常量里、官方无对应端点的路径按 274 则无处取数。
2. **spec 的交付形态**：只给 **判定规则 + 可复现的取数方法**（从哪个官方页、按什么步骤把一条端点映射成表条目），**不列最终数值表**——后者是施工，Out of scope 已排除。表条目形状（二元组还是容纳计数维度 / 任意窗口）由 [限额表条目要不要容纳计数维度与任意窗口](08-limit-entry-shape.md) 决定，03 不预设。
3. **决策归属**：第 1 点标注为「已由 02 决定」，本工单不重开「限不限流 / 兜不兜底」；README.md:113 免责声明的具体行文归 [文档、CHANGELOG 与 ADR 怎么落](07-docs-and-adr.md)。「一个决策只住一处」。
4. **事实缺口**：Q1 的验收线需要一份「官方已公布限额的端点清单」才能落地，而 findings 只有约 135 的统计、没有清单，274 与 135 的差异原因也未查。按 Notes 的「事实与决策分工」，新开 [官方已公布限额的端点清单与 274/135 差异核对](09-official-limit-endpoint-list.md)（AFK research，blocked by 03），本会话不解。
5. **测试断言口径**：要断言，但口径是 **「每个在验收线集合里的路径都在 `RATE_LIMITS` 里」**，不是「274 个路径都在表里或显式豁免」。验收线集合由 09 的清单产出，故断言实现 blocked by 09、属图外施工；03 只定口径，不写断言、不定测试文件位置。

## 边界

- 表仍是 8 条：本工单定的是「应该覆盖到什么程度」的**验收线**，不是把表补全；补全属图外施工，spec 不承诺补全进度。[两个默认开关是否从 off 改 on](05-default-switches.md) 里「表只有 8 条端点」的前提因此不变。
- 条目形状归 [限额表条目要不要容纳计数维度与任意窗口](08-limit-entry-shape.md)、窗口与共享语义归 [限流器形态与共享边界](06-limiter-shape.md)、文档行文归 [文档、CHANGELOG 与 ADR 怎么落](07-docs-and-adr.md)；官方数值变更的维护流程已 graduate 为 [官方 Change Log 变更时表怎么同步](10-changelog-sync.md)。
- 本图只决策，不改 `okx/consts/rate_limits.py` / `okx/rate_limit.py`。
