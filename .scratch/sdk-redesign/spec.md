# SDK 设计整改

python-okx 的缺陷与结构性问题整改计划。**状态：12 条全部交付于 0.5.0**（0.4.5 发布 01–06，0.5.0 发布 07–12）。来源：2026-11-04 的设计评审。决策记录见 `docs/adr/0001-release-strategy.md` 与 `docs/adr/0002-errors-raise-by-default.md`。

## 判断

这是「薄封装 + 全量端点镜像」型 SDK：端点与常量分离、单测无副作用，方向是对的。问题在于全部横切关注点（认证、序列化、错误、类型）压在 `OkxClient` 一个基类里，随端点增长以复制粘贴的形式扩散。

## 发布切分

**0.4.5 —— 只修缺陷，不动公共契约。** 缺陷不该在用户手里多等一个版本。

**0.5.0 —— 一次性承接所有破坏性改动。** 与缺陷修复分开，否则 0.5 一旦回归无法判断成因。不为旧参数名保留别名：`ugly` 这类拼写错误留到 1.0 意味着每个新读者都要学两套名字，而 0.5 本来就是 breaking 窗口。

## 范围外

- **WebSocket 层**：日志体系与 REST 层分裂、工厂连接失败返回 `None`、`ConnectionClosedError` 直接 re-raise、回调同步阻塞。单独立项——WS 的失败模式（重连、乱序、回压）需要独立验收标准，混进来会模糊 0.5.0 的回归面。
- **分页迭代器、限流、重试、`clOrdId` 幂等辅助**：等 0.5.0 落地后再评估是否仍需要。

## 结论

0.4.5 的验收线是 contract 测试通过；0.5.0 的验收线是迁移表上的每一处改名都有对应记录，且旧代码在新版本下失败时能看懂原因。
