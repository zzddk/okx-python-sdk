# WebSocket 回调契约：async def、按序串行、异常隔离

0.9.0 之前回调在事件循环里同步调用：慢回调阻塞整条流，抛出的异常直接终止 `consume`，连接随之不可用。心跳与重连要落地，读循环就不能被回调拖住，也不能被回调杀死。

我们决定：**回调可以是 `async def`**。返回值可等待时 await，否则按普通函数内联调用（兼容 0.8 的写法）。回调抛出的任何异常都记日志后丢弃该条消息，读循环继续。回调按消息到达顺序串行执行；并发只存在于心跳与读循环之间，不由 SDK 为每条消息创建任务。`pong` 属于心跳协议，不进入回调。

## Considered Options

- **强制同步 + 捕获异常**：兼容性最好，但慢回调仍占用事件循环，心跳与重连都拿不到执行机会，等于没有解决第 8 条的一半。
- **每条消息一个 task**：读循环不会被阻塞，但会丢掉顺序——下单确认与行情、撤单确认与账户推送的相对顺序都可能反了；慢消费者还会造成无界并发。
- **拒绝同步回调**：契约最纯，但每个已有用户都要改一行，而这一行并不带来新的安全保证。

## Consequences

- 回调在读循环里被 await，所以慢回调会推迟后续消息与 `pong` 的读取；超过 `ping_timeout` 会被判为连接失效并重连。回调内部的长任务应由调用方 `create_task` 卸载。
- SDK 只承诺按到达顺序串行调用；回调内部若要并发，由调用方自己决定。心跳任务只发送 `ping`，不调用用户回调，所以这个“串行”没有例外。
- 同步回调仍然可用，但它阻塞事件循环，文档与 CHANGELOG 都要求新代码使用 `async def`。
- `pong` 不再出现在回调的数据流里；原本依赖它的代码需要改用心跳状态（目前不对外暴露）。
- 连接丢失同样不进回调流（2026-11-05 补记）：socket 自己断开时，监督者调 `on_lost(exc)`，会话只拿它中断进行中的握手。用户侧的信号是 `start()` 返回的 task——`reconnect=False` 时抛出，否则等重连与重放。此前这里会伪造一条 `{"event": "error", "code": "ConnClosed"}` 帧塞给回调，与 `pong` 的理由相同：它是连接状态，不是服务端发来的消息。
