# 发布策略：缺陷补丁先行，破坏性改动集中到 0.5.0

python-okx 已发布在 PyPI 并被外部依赖，但仓库里同时存在两类问题：一类是确定的缺陷（`GET_OPTION_TRADES` 在 `consts.py` 中重复定义导致后者静默覆盖前者、无 HTTP 状态码检查、`use_server_time` 被硬置为 `False`、12 处可变默认参数），另一类是必须动公共契约才能修的设计问题（`ugly` 应为 `uly`、`''` 与 `None` 两套空值约定、返回裸 dict）。

我们决定：**0.4.5 只修缺陷，0.5.0 一次性承接所有破坏性改动**，且 0.5.0 不为旧名保留别名。

## Considered Options

- **全部塞进 0.5.0**：缺陷要在用户手里多待一个版本，且一旦 0.5 出现回归，无法判断是缺陷修复还是重构引入的。
- **0.5.0 为旧参数名保留别名 shim**：`ugly`、`set_risk_offset_typel` 这类拼写错误会一直活到 1.0，每个新读者都要学一遍两套名字。迁移成本只是 CHANGELOG 里一张「旧名 → 新名」表。

## Consequences

- 0.4.5 必须包含一层 contract 测试：遍历所有 `*API` 类的方法，断言 `(HTTP method, path)` 落在常量表内且常量名唯一。没有这层测试，同类覆盖缺陷仍会复发。
- 0.5.0 需要一份迁移说明，而不是一句「breaking change」。
