Repro · 同一监督者，只换异常类型
$ 构造 FakeConnector，socket 直接抛异常 ConnectionClosedOK -> task raised ConnectionClosedOK | on_lost calls: 0 ConnectionClosedError -> task raised ConnectionClosedError | on_lost calls: 1
ConnectionClosedOK 是 ConnectionClosed 的子类，不是 ConnectionClosedError 的子类。

问题：_read() 只捕获 ConnectionClosedError。真实服务器的正常关闭（1000/1001）走 ConnectionClosedOK，既不通知 on_lost，也不中断进行中的登录握手；docstring 却承诺「A closed connection is reported to on_lost」。

方案：捕获基类 ConnectionClosed（或单独补 OK），让关闭语义只分「自己停的」和「连接没的」两种；补一个 ConnectionClosedOK 的用例，锁住 on_lost 被调用。

  • · 一行改动 + 一个新用例
  • · 登录不再空等 10s
  • · 日志不再把正常关闭记成 warning
  • · 与 docstring 重新一致
  • · 要定 reconnect=False 时正常关闭算不算错误
如果希望「正常关闭」在 reconnect=False 下表现为 task 正常结束，而不是抛异常，需要让 _read 返回一个结束原因；只把 except 放宽会把两种关闭都当失败。

03 · 重连把永久失败当瞬时失败：task 永远不结束

Correctness

okx/websocket/connection.py:188-210 · okx/websocket/WsBaseAsync.py:207-214 · okx/websocket/login.py:80-86

Before · 所有异常都进同一条循环

  RC --> O["_open()"]
  O --> RD["on_ready()

  RD -- "登录被拒 / proxy 不支持" --> X["except Exception"]
  X --> SLEEP["sleep 1s → 60s"]

  RD -- 成功 --> LIVE["连接可用"]
  classDef bad fill:#fef2f2,stroke:#dc2626,color:#7f1d1d
  class X,SLEEP bad
After · 先分类，再决定重试
transient → backoff → retry
permanent → task 以原异常结束
（登录拒绝、proxy 能力缺失、URL 非法）

start() 返回的 task 是唯一能报错的地方；ADR-0005 已经这么承诺，只是重连路径没做到。

问题：_reconnect() 的 except Exception 把「凭证被拒」「websockets 不支持 proxy」这类不会自愈的错误也当成网络抖动，按 1s→60s 无限重试。start() 之后用户机器上只剩日志里的 Reconnect failed，task 永远不结束。

方案：把「这次失败能不能靠重试修复」变成一个显式判据：登录握手抛出的 ConnectionError 用一个专门类型（或 error code）标成永久，能力缺失用 RuntimeError 标成永久，其余才进退避。

  • · 永久失败终于能被调用方看见
  • · 不再无限打日志
  • · 与 ADR-0005 的 task 语义对齐
  • · 需要给握手错误一个类型，不能靠文案匹配
  • · 首次连接与重连走同一条判据
LoginHandshake.rejection() 现在抛的是普通 ConnectionError，与「网络断了」共用类型。分类前先给它一个 LoginRejected 子类，否则只能把两者一起当永久，会把可恢复的断线也停掉。

与 login_payload(timestamp=...) 同构：固定向量已经覆盖了 HMAC 原语，缺的是 REST 的拼接规则。

  • · 静态时间戳让断言可重复
  • · GET 与 POST 的拼接差异被锁住
  • · 不触网、不依赖私钥
  • · 只多一个构造参数

05 · raise_on_error=False 的文档与行为相反

Worth exploring

README.md:117 · okx/transport.py:121-128 · test/unit/okx/test_retry.py:121 · .scratch/rate-retry-policy/spec.md:90,94

Before · 文档说「不重试」，代码重试了 3 次
Transport(raise_on_error=False, max_retries=2) GET /api/v5/public/time → ConnectError raised ConnectError | attempts: 3
_retry_allowed() 只看 replayable 与 max_retries，不看 raise_on_error。测试只覆盖「业务码以 payload 返回」，名字却叫 never_retries。
After · 一句话说清两条边界
业务错误：raise_on_error=False 时以 payload 返回，不重试。

网络错误：仍然重试；POST 仍受 replayable 约束。
代码行为是合理的：GET 重试安全，POST 没幂等键不重试。要改的是 README 与 spec 的措辞，以及测试名。

问题：把 raise_on_error=False 当「完全关闭重试」用的调用方会得到相反的行为；spec 第 5 节写了同一句错话，下一个施工者会照抄。

方案：以代码为准改文档：业务错误返回 payload、网络错误仍重试；测试改名成 test_business_error_payload_is_returned_without_retry，再加一个「网络错误仍然重试」的用例把边界锁死。

  • · 两处文档一起改
  • · 测试名不再撒谎
  • · 行为不变，无迁移成本
  • · 加一条反向用例
如果原意确实是「raise_on_error=False 就完全不重试」，那要改的是 _retry_allowed()；但这样会让 GET 的网络抖动退化为一次失败，需要重新评估默认值。

RateLimiter 本身被测得很细，但没有一个用例让 request() 在 rate_limit=True 下真的走一遍；删掉这两行，856 个测试仍全绿。

Before · 两个 login 互相覆盖握手
await asyncio.gather(ws.login(), ws.login()) → self._handshake 被第二个覆盖 → 第一个等满 DEFAULT_LOGIN_TIMEOUT

私有客户端 start() 已登录，日常触发面小；但订阅路径一旦被并发调用，就会出现 10 秒空等。

问题：前者是「回归不会被发现」，后者是「共享状态没有单写者」。两处都不大，但都属于测试与结构一起失守的位置。

方案：限流加一个 rate_limit=True + 注入 sleep 的请求级用例；登录把 in-flight handshake 存下来复用（或加 asyncio.Lock），让并发调用共享同一次握手。

  • · 接线处有回归保护
  • · 并发登录只发一次请求
  • · 不需要新模块
  • · 登录锁只在会话内，无跨连接共享
复用 in-flight 握手要处理「第一个失败后第二个还能重试」；直接锁住整个 login() 更简单，但要确认它不会被 _on_ready 的重入卡死。
